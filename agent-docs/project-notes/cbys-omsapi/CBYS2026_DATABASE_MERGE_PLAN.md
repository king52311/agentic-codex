# cbys2026 数据合并实施方案

## 1. 目标与库关系

本次不是三个完全独立数据库之间的全量合并，而是基于同一业务库演进的增量合并：

| 数据库 | 定位 | 时间/来源 | 处理原则 |
|---|---|---|---|
| `cbys` | 业务数据主库 | 当前正在使用，数据较新 | 旧业务数据以它为准 |
| `djwms` | 结构和功能参考库 | 2026 年 8 月由 `cbys` 备份后改造 | 作为新表、新字段、新功能数据来源 |
| `cbys2026` | 最终运行库 | 新建空库或待初始化库 | 最终 API 只连接此库 |

由于 `djwms` 是 8 月份 `cbys` 的备份，绝大多数旧表、旧数据和主键是一致的。因此不采用“整库逐行覆盖”，而采用“共同基线 + 双库增量合并”：

```text
cbys（当前业务数据）
       ├── 旧业务数据增量 ───────┐
       │                         ├── cbys2026
djwms（8月备份后改造）             │
       ├── 新表/新字段/新功能数据 ┘
       └── 改造结构和索引
```

## 2. 总体策略

### 2.1 结构来源

以 `djwms` 的当前表结构作为目标结构标准，先将 `cbys2026` 结构补齐，再迁移数据。

结构处理包括：

- `djwms` 新增表；
- `djwms` 在原表新增的字段；
- 字段类型、长度、默认值、注释变化；
- 主键、唯一键、普通索引；
- 必要的视图、存储过程和初始化配置；
- 外键暂不盲目启用，待数据校验完成后再确认。

原有字段如果两库定义冲突，先生成差异报告，不自动覆盖生产基线；只有确认属于新功能所需改造时，才生成迭代 SQL。

### 2.2 旧业务数据来源

旧业务数据统一以 `cbys` 为准：

- `cbys` 有、`cbys2026` 无：插入；
- 两边主键相同：保留 `cbys`；
- `cbys` 的更新时间更新：按 `cbys` 回写；
- `djwms` 中仅因 8 月备份产生的旧数据：不覆盖 `cbys`；
- `djwms` 独有且无法确认属于新功能的数据：只列入冲突清单，不自动导入。

### 2.3 新功能数据来源

新功能数据来自 `djwms`，但必须区分“新增功能数据”和“旧业务数据”：

- 新增功能表：复制 `djwms` 数据；
- 新增字段对应的配置数据：复制 `djwms` 数据；
- 新增菜单、权限、角色、系统配置、定时任务：按业务编码合并；
- 新增价格、阶梯、违约金、抄表册、抄表计划、账单批次等业务数据：按唯一业务键合并；
- 与旧表重复的数据：不按自增 ID 直接覆盖。

## 3. 表分类与数据规则

正式执行前先生成表分类清单，不能只按表名判断。

### A 类：基础旧业务表

例如用户档案、表具、账户、充值流水、抄表历史等。

- 结构参考 `djwms`；
- 数据以 `cbys` 为准；
- 通过主键或业务唯一键同步到 `cbys2026`；
- 保留 `cbys` 的余额、流水、历史读数和状态；
- 不直接导入 `djwms` 中同主键旧数据。

重点表：

```text
newsun_userprofiles
newsun_meter
newsun_account
newsun_payment
newsun_altermoney
ecu
ecu_history
```

### B 类：改造后的新功能表

例如抄表、出账、计划任务和收费工作台相关表。

- 以 `djwms` 结构为准；
- `cbys2026` 缺表时创建；
- `cbys` 有对应历史数据时按业务键迁移；
- 仅存在于 `djwms` 的新业务记录可导入；
- 涉及账户余额或扣费的记录必须先核对流水，不能重复执行扣款。

重点表以实际结构扫描结果为准，预期包括：

```text
reading_book
reading_book_meter
reading_plan
reading_activity
reading_billing_batch
reading_billing_detail
reading_task_log
```

### C 类：系统配置、字典、菜单权限表

不能简单按自增 ID 合并，应按稳定编码或业务名称匹配：

```text
sys_menu
sys_role
sys_role_menu
sys_operator
sys_operator_role
basic_code
sys_site_config
sys_task_config
```

处理规则：

- 菜单按 `url + component` 或稳定业务标识匹配；
- 字典按 `codeType + codeValue` 匹配；
- 系统配置按配置键匹配；
- 角色按角色编码匹配；
- 角色菜单关系通过目标库新 ID 重建；
- 用户账号以 `cbys` 为准，新增功能角色和权限从 `djwms` 补齐；
- 不覆盖现有账号密码、启用状态和组织关系，除非差异清单确认。

### D 类：人工备份、临时和历史留存表

默认不迁移：

- 临时导入表；
- 手工备份表；
- 已废弃业务表；
- 只用于人工查询的历史副本；
- 无程序引用且无外键依赖的旧表。

是否排除以代码引用、Mapper、SQL、定时任务和表关联扫描结果为依据。不会因为表名看起来像历史表就直接删除。

## 4. 执行阶段

### 阶段一：只读盘点

连接三个数据库，只读获取：

- 表和字段元数据；
- 主键、唯一键、索引；
- 表行数、最大 ID、最大更新时间；
- 关键表业务唯一键重复情况；
- 程序实际引用的表；
- `djwms` 相对 `cbys` 的新增表、字段、索引和数据。

输出：

```text
cbys2026_schema_diff.md
cbys2026_table_classification.md
cbys2026_data_diff.md
cbys2026_conflict_report.md
```

这一阶段不写入任何数据库。

### 阶段二：建立目标结构

按以下顺序生成结构 SQL：

1. 创建缺失的 `djwms` 新表；
2. 为已有表补充缺失字段；
3. 补充索引和唯一约束；
4. 创建必要的初始化配置；
5. 暂不执行删除字段、删除表、清空数据、重命名字段等破坏性操作；
6. 对 XML、Mapper 和 SQL 做语法校验。

目标库应保留一份可复现的结构脚本，不直接修改 `djwms` 基线文件。

### 阶段三：迁移 `cbys` 业务数据

数据导入顺序遵循父表到子表：

1. 小区、组织、字典和基础配置；
2. 用户档案；
3. 表具和表具实时状态；
4. 账户；
5. 账户充值、退费和扣费流水；
6. 表具历史读数；
7. 抄表册及表册成员；
8. 抄表计划及抄表活动；
9. 出账批次、账单明细和任务日志。

对旧业务表执行“目标不存在则插入，存在则以 `cbys` 更新”的幂等脚本。账户、流水、历史读数不得只按自增 ID 判断，必须同时核对 `profilesId`、`ecuId`、流水号、计划号或账单号等业务键。

### 阶段四：合并 `djwms` 新功能数据

只导入经过分类确认的数据：

- 新功能表的整表数据；
- 新菜单及权限；
- 新字典项；
- 新系统配置；
- 新价格、阶梯、违约金模板；
- 新抄表和出账配置。

涉及自增 ID 的表，先建立旧 ID 到目标 ID 的映射，再导入关联表：

```text
旧表 ID -> 目标表 ID
用户 ID -> 用户角色关系
角色 ID -> 角色菜单关系
小区 ID -> 用户、表册、计划关系
表册 ID -> 表册成员、计划关系
计划 ID -> 抄表活动、出账批次关系
```

### 阶段五：一致性校验

至少校验以下内容：

- 关键表行数；
- 主键和唯一键重复；
- 用户档案与表具关联；
- 一户多表关联；
- 账户余额与账户流水；
- 充值、退费、扣费流水总额；
- 抄表历史的表号和时间范围；
- 抄表册、计划、活动的关联；
- 账单状态、账单金额和结算流水；
- 菜单、角色、用户权限；
- 定时任务配置和执行日志；
- API 关键接口返回结果。

账户和扣费校验建议使用汇总对账：

```text
账户当前余额
= 初始余额 + 充值金额 - 退费金额 - 扣费金额 + 手工调账金额
```

实际字段和正负号以当前 API 计费实现为准，不能直接假设所有流水金额同号。

## 5. SQL 与脚本组织

建议在 `omsapi/db/migrations/` 下新增独立合并脚本，不复用有循环依赖的 Alembic 版本：

```text
cbys2026/
├── 00_precheck.sql
├── 01_schema_from_djwms.sql
├── 02_merge_cbys_base_data.sql
├── 03_merge_djwms_new_feature_data.sql
├── 04_merge_menu_permission_config.sql
├── 05_add_indexes.sql
├── 06_validation.sql
└── README.md
```

脚本要求：

- 可重复执行；
- 每一步有执行记录；
- 尽量使用事务；
- 插入使用业务键去重；
- 不生成删除和清空语句；
- 大表分批处理；
- 记录源库、目标库、执行时间和脚本版本；
- 生产执行前导出差异报告。

`cbys2026` 的结构最终稳定后，再把确认过的结构变更拆分为正式环境可执行的迭代 SQL。基线文件仍保持原始版本，不用目标库反向覆盖基线。

## 6. 关键风险和处理

### 主键相同但业务数据不同

这是同源备份后最常见的情况。默认保留 `cbys`，将 `djwms` 差异写入报告；只有确认是新功能记录才导入。

### 自增 ID 不一致

不能直接复制关联表。使用业务键查询目标 ID，并保存映射表。

### 新功能使用旧表新增字段

先补字段，再导入数据；字段默认值必须与 API 实体和 Mapper 的空值处理一致。

### 账户和流水重复

禁止按导入次数直接累加余额。先核验流水唯一键，再按 API 既有逻辑重算或校验余额。

### 菜单权限重复

按路径、组件名、角色编码、字典编码合并，不能按自增 ID 覆盖，否则可能造成权限串线。

### 删除类差异

发现 `djwms` 比 `cbys` 少表、少字段或少数据时，只记录差异，不自动删除。删除 SQL 必须单独确认。

## 7. 切换与回滚

### 切换

1. 停止 API 和采集服务；
2. 备份 `cbys2026`；
3. 执行结构和数据合并脚本；
4. 执行校验脚本；
5. 将 API 和采集项目数据库配置改为 `cbys2026`；
6. 启动 API；
7. 验证登录、权限、档案、充值、账单、抄表、出账和定时任务；
8. 再启动采集服务；
9. 观察日志和关键数据变化。

### 回滚

- API 配置切回原数据库；
- 停止新库上的写入服务；
- 保留 `cbys2026` 快照、执行日志和冲突清单；
- 不反向覆盖 `cbys`；
- 如需修正，只对 `cbys2026` 生成新的补丁 SQL。

## 8. 最终验收标准

满足以下条件后，才允许把 `cbys2026` 作为正式运行库：

- 结构覆盖 `djwms` 的新功能要求；
- `cbys` 关键旧业务数据完整；
- 账户、流水、余额对账一致；
- 一户多表、抄表、账单、结算关系完整；
- 菜单和角色权限可正常使用；
- API 编译、启动和关键接口验证通过；
- 采集服务可正常写入；
- 差异报告中所有高风险冲突均已处理；
- 所有数据库变更均有可重复执行的迭代 SQL；
- 未执行任何未经确认的删除类 SQL。
