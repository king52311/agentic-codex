# Java 后端通用规范

## 分层边界

- Controller 只负责参数接收、基础校验、调用 Service、返回结果。
- 业务判断、数据组装、事务控制、第三方接口调用应放到 Service 或业务组件。
- Mapper/DAO 只负责数据访问，避免承载复杂业务判断。
- 禁止跨层调用；接口、任务、消费者入口都应收敛到清晰的业务服务。

## SQL 与数据模型

- SQL 查询结果优先使用 Entity、DTO、VO、Response 等明确类型。
- 字段完全动态时才使用 `Map<String, Object>`。
- SQL 字段要明确列出，避免长期使用 `select *`。
- 高频接口和大数据量查询必须关注索引、查询条件、返回字段数量和分页策略。
- 大数据量任务必须分页或分批处理，避免一次性加载过多数据到内存。
- 建表语句优先使用普通索引、唯一索引表达关系约束；是否使用数据库外键以项目规则为准。

## 注释要求

- 新增或修改 Java 类时，按项目约定维护类注释。
- 新增或修改方法时，维护必要的方法注释，说明功能、入参、返回值、边界条件或异常行为。
- 复杂逻辑、关键判断、特殊兼容、性能优化代码要说明“为什么这样做”。
- 禁止无意义注释，例如“处理数据”“执行方法”“设置值”。

## 性能要求

- 禁止在大循环中反复查询数据库，优先批量查询、批量插入、批量更新。
- 避免重复远程调用、重复 JSON 转换、重复计算。
- 定时任务、批处理、导入导出要限制批次大小，并记录耗时。
- 使用缓存时必须明确 key、TTL、失效策略和一致性边界。

## 定时任务与批处理

- 循环处理多条数据时，单条数据应独立 `try-catch`。
- 单条失败只记录日志并继续处理，避免中断整个任务。
- 任务结束输出汇总日志：总数、成功数、失败数、耗时。
- 分布式部署下要考虑重复执行、并发执行和锁机制。

## 第三方接口与日志

- 调用前记录接口名、业务 id、关键入参。
- 调用后记录接口名、业务 id、耗时、返回状态、关键返回字段。
- 异常时记录接口名、业务 id、异常堆栈。
- 密码、token、secret、手机号、身份证号等敏感信息必须脱敏。
- 禁止使用 `System.out.println`，统一使用日志框架。
- 高频循环日志要控制数量，避免刷爆日志。

## 异常与事务

- 禁止空 `catch`，禁止 `e.printStackTrace()`。
- 捕获异常后必须记录日志，必要时转换为业务异常向上抛出。
- 不要为了“让代码不报错”随意吞异常。
- 多表写入、状态变更、扣减、余额变更等场景必须明确事务边界。
- 避免在事务中执行耗时第三方接口调用。

## 安全要求

- 对外接口入参必须做必填、长度、格式、范围校验。
- 集合参数应限制最大数量。
- 关键 id、状态值、枚举值不能直接信任前端传参。
- 数据库密码、Redis 密码、token、secret、第三方 key 禁止硬编码。
- 涉及权限、租户、数据范围的查询必须明确鉴权和过滤条件。

## 自检要求

- 修改后优先运行相关模块编译或测试。
- 修改 SQL 时说明影响范围，并用最小数据场景验证。
- 修改核心流程、定时任务、第三方接口时，说明测试场景和结果。
- 受环境限制无法验证时，明确说明原因和剩余风险。
