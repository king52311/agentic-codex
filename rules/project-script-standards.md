# 项目脚本通用规范

## 放置位置

- 项目根目录可以放少量高频快捷脚本，例如 `build.sh`、`deploy.sh`、`release.sh`、`start.sh`。
- 复杂脚本建议放到 `scripts/` 目录，根目录只保留入口脚本。
- 脚本命名要表达结果，不使用临时含义的名称，例如 `test2.sh`、`new.sh`。

## 脚本职责

- 一个脚本只承担一类任务：构建、启动、发布、自测、数据修复不要混在一起。
- 高频命令可以封装，低频高风险操作要保留确认和说明。
- 脚本内不要写死个人本机路径，优先基于脚本所在目录计算项目根路径。
- 环境差异通过参数或环境变量传入，不在脚本里散落多套硬编码。

## 前端构建命令优先级

- 前端项目根目录存在 `build.sh` 时，构建、验证和打包必须优先执行 `./build.sh`，并按脚本约定传入测试、正式等环境参数。
- 不得在已有 `build.sh` 的项目中绕过脚本直接执行 `npm run build`、`pnpm build` 或 `yarn build`，避免遗漏环境变量、压缩包生成和项目自定义步骤。
- 仅当项目不存在 `build.sh` 时，才检查锁文件和 `packageManager` 配置，选择对应的 npm、pnpm 或 yarn 构建命令。
- `build.sh` 无执行权限时可先补充执行权限；脚本自身失败时应排查并修复脚本，不直接改用包管理器命令掩盖问题。

## 参数设计

- 支持 `-h` 或 `--help` 输出用法。
- 支持明确的目标参数，例如模块名、环境名、版本号。
- 参数缺失时给出可读错误，不静默使用危险默认值。
- 对生产环境、数据删除、远程发布等操作增加二次确认或 dry-run。

## 输出与失败处理

- 输出当前目录、目标模块、目标环境、版本号等关键上下文。
- 使用 `set -e` 或显式错误检查，失败后及时退出。
- 关键命令执行前打印命令意图，执行后打印结果。
- 不吞错误，不用无意义的 `|| true` 掩盖失败。

## 安全要求

- 密码、token、私钥不写入脚本。
- 需要凭证时从环境变量、CI Secret 或本机安全配置读取。
- 发布脚本不自动执行破坏性 Git 操作。
- 脚本生成的临时文件、日志、构建产物应确认是否需要加入 `.gitignore`。

## 文档要求

- 新增通用脚本时，同步补充 README 或 `docs/` 使用说明。
- 说明脚本目标、参数、示例、依赖工具、适用环境、风险点。
- 若脚本依赖外部服务，说明连接信息来自哪里。

## Git 忽略建议

- 业务项目中的本地快捷脚本默认不纳入版本控制，推荐忽略：`start.sh`、`stop.sh`、`build.sh`。
- 业务项目中的 Agent 过程文档、临时说明、排查记录类 `.md` 默认不纳入业务仓库版本控制，推荐忽略：`*.md`。
- 需要保留在业务仓库的正式文档，用 `.gitignore` 白名单单独放开，例如：`!/泵站综合得分计算说明.md`。
- 已经被 Git 跟踪的文件，新增 `.gitignore` 后不会自动忽略；需要执行 `git rm --cached <file>` 取消跟踪，并保留本地文件。
- 后续 Agent 相关 Markdown 文档统一沉淀到 `agentic-codex/agent-docs/`，再按主题整理到规则、流程或架构目录。
