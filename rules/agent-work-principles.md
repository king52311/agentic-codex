# Agent 通用工作原则

## 先理解，再修改

- 先阅读现有实现，再决定改动位置。
- 搜索相似页面、接口、模型、Schema、工具函数和样式约定。
- 不要一上来重写已有结构。
- 优先在现有模块边界内做小步改动。

## 保持项目风格

- 优先复用项目已有框架、组件、工具函数、异常格式和命名方式。
- 非必要不新增抽象层。
- 非必要不引入新依赖。
- 前后端同一概念保持命名一致。

## Agent 文档落地

- 所有项目的 Agent 相关 Markdown 文档统一写入 `agentic-codex` 项目对应目录。
- 不再把 Agent 规则、上下文、排查记录、执行约定等文档写入业务项目根目录。
- 写完 Agent 相关 Markdown 后，必须在 `agentic-codex` 中先执行 `git pull --rebase`，再执行 `git add`、中文 `git commit`、`git push`。
- 若业务项目需要入口文件，只保留必要引用入口，具体内容沉淀到 `agentic-codex`。

## 架构边界

- 路由层负责请求、鉴权和响应组织。
- 业务逻辑优先放在 service 或项目已有业务层。
- 数据结构变更要同步检查模型、Schema、接口返回、前端类型和文档。
- 共享能力优先抽成公共组件、hook、工具函数或服务，不在业务页重复实现。

## 禁止行为

- 未确认现有实现前大面积重构。
- 未获用户明确授权，不得删除、改写、禁用或以安全判断等理由改变用户既有代码的业务逻辑。对于无法执行的新增请求，应说明无法执行的范围；不得借此修改用户原有实现。
- 未补迁移就只改数据库模型。
- 在前端硬编码后端返回结构的猜测字段。
- 绕过权限校验。
- 提交密钥、Token、账号密码。
- 为小改动引入重量级依赖。

## 结果说明

- 说明改了什么。
- 说明验证结果。
- 涉及配置、依赖、数据库、生产数据时说明影响范围。
